# AvatarEmoji

The avatar for a concept or reaction shown as an emoji.

---

## Overview

### Purpose

- Represent a concept, mood or reaction with a single emoji
- Add a lightweight, recognizable marker to items in lists and headers
- Offer an expressive alternative when an entity has no photo or icon

### Anatomy

An emoji avatar is square and renders a single emoji as a twemoji image.

### Sizes

The supported scale is narrower than the shared avatar scale: only `sm`, `md`,
`lg` and `xl` exist here. `xs` and `2xl` are valid elsewhere but not on this
component, and passing one leaves the avatar box with no size class at all (the
emoji image keeps its own 16px default), so validate
the value before forwarding it from a generic avatar wrapper.

## Guidelines

### Design best practices

#### When to use

- The content is always a single emoji
- Reactions, lightweight category markers, expressive placeholders

#### When NOT to use

- The entity type is dynamic: use `F0Avatar`
- You need a system icon rather than an emoji: use `F0AvatarIcon`
- The value comes from free user input and may be a skin-toned emoji, a flag, or
  a short string: validate it first, or every miss silently becomes 🤔

## Behavior

`emoji` accepts exactly **one code point**, optionally followed by the U+FE0F
variation selector. Anything else is replaced with 🤔 at render time, and the
value you passed never reaches the DOM. That is stricter than "is this an
emoji": multi-code-point sequences — skin-tone modifiers (`👍🏽`),
regional-indicator flags (`🇪🇸`), and ZWJ sequences — all hit the same fallback
as junk input.

<Canvas of={EmojiStories.InvalidEmoji} />

One case slips past the check. A value can match the regex and still have no
twemoji asset behind it (`#`, `1`, `*`). Those render as the raw character
instead of an emoji image, so you get the glyph in the page's own typeface rather
than the pictographic look the component is for. Prefer a pictographic emoji.

---

## Accessibility

The emoji is rendered as an `<img>` whose `alt` is the emoji character itself, so
a screen reader announces the glyph (or the platform's name for it), never what
it means in your UI.

- Treat the avatar as decoration and keep the meaning in adjacent visible text.
  A row that reads only "🍑" tells a screen-reader user nothing about why it is
  there.
- Don't rely on `aria-label` / `aria-labelledby` to supply that meaning. The
  props exist, but they land on a `<div>` with no `role`, where ARIA prohibits
  them, so assistive technology is not required to honour them. There is also no
  way to override the image's `alt`.
- **The mount animation ignores reduced-motion.** `EmojiImage` scales the glyph
  from 0.75 to 1 over 600ms every time it mounts, without consulting
  `useReducedMotion()`. It is a known gap, not a decision: a row of emoji avatars
  animates on every render for a user who asked the OS for less motion. Not an AA
  failure (WCAG 2.3.3 is AAA), and axe cannot see it.
