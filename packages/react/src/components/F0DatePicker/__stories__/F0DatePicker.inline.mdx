# DatePicker / Inline

The inline `F0DatePicker` puts a date inside a record row: it reads as text where a read-only row would print its value, and only becomes an input once someone decides to change it. For a date in a form, use the default variant; for a date inside a table cell, use `OneDataCollection`'s editable table.

## Anatomy

<Controls of={Stories.DetailRow} />

The row is borderless and fills its container, so the value lines up with the read-only rows above and below it. The label is the accessible name and is never shown visually — the row's own label column carries it.

### Variants

Who may do what comes from two props, both meant to be passed conditionally from whatever the caller already knows about the reader.

| `readonly` | `onRequestChange` | What the reader gets                                                                         |
| ---------- | ----------------- | -------------------------------------------------------------------------------------------- |
| —          | —                 | The calendar on hover or focus. Activating the row opens the picker on the date already set. |
| `true`     | a handler         | A request action instead. There is nothing to edit.                                          |
| `true`     | `undefined`       | Nothing. The date is inert text.                                                             |

```tsx
<F0DatePicker
  variant="inline"
  label="Seniority date"
  value={date}
  onChange={setDate}
  readonly={!canEdit}
  onRequestChange={canRequest ? handleRequest : undefined}
/>
```

The inline variant keeps the props a record row still needs — `required`, `clearable`, `error`, `status` and `hint` — and drops the rest of the field chrome. `size`, `disabled`, `hideLabel`, `labelIcon`, `transparent`, `loading`, `open` and `showIcon` are typed `never`, so passing one is a compile error rather than a silent no-op.

### Copying

`copyable` gives the row the same hover treatment an editable one has, and puts a copy action in the strip. On a `readonly` row it is the only action there; alongside an editable one it follows the calendar, the way the prototype's Employee number row carries both.

<Canvas of={Stories.DetailRowCopyable} />

<Canvas of={Stories.DetailRowEditableAndCopyable} />

Copying turns the row and the icon positive and swaps the icon for a check for 1.4s. The strip is pinned open for that stretch, so moving the pointer away does not take the confirmation with it, and the button carries `aria-live="polite"` so it is announced. A clipboard write the browser blocks produces no confirmation at all — a check the reader cannot trust is worse than none.

## Guidelines

### Design best practices

**When to use**

| Situation                        | Use the inline variant when                                                                                                  |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| A record detail page             | The date is one row among many, most of which are read-only, and the row should not look like a form field until it is used. |
| A date the reader may not change | Permission varies by reader and the row still has to render for everyone.                                                    |
| A row that must not reflow       | The read and edit states are the same height, so revealing the input never moves the rows below it.                          |

**When not to use**

| Situation                                  | Use instead                                                                                                 |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| A date in a form                           | The default `F0DatePicker` variant — it carries the label, validation, `status` and `hint` the form needs.  |
| A date in a table cell                     | `OneDataCollection`'s editable table, which owns cell focus, keyboard grid navigation and row-level saving. |
| A range, or a granularity the reader picks | The default variant — inline is built for a single settled value read at a glance.                          |
| A date that is always being edited         | The default variant — inline's whole point is that it reads as text first.                                  |

### Content best practices

- The `label` is the accessible name. Write it as the field is named in the record, not as an instruction.
  - **Correct:** "Seniority date", "Contract start date"
  - **Incorrect:** "Pick a date", "Select seniority date"
- Use `placeholder` for what an empty row should say. It defaults to the translated `date.none` ("None").
  - **Correct:** "no date", "Not set"
  - **Incorrect:** "dd/mm/yyyy" — the format belongs in the input, not in the read state.

### Behavior

- The date reads as `dd/MM/yyyy`: `displayFormat` defaults to `"default"` here rather than `"long"`, and that format carries into the input, so the value does not reformat when the row is activated.
- Editing is a detour, not a state the caller owns. Activating the row opens the picker; committing a date or dismissing the calendar puts it back to text. `onModeChange` reports both transitions for a caller that wants to pin a hover state or log the interaction, but nothing needs to be wired for the swap to work.
- The read and edit states are both 32px, taken from the same `inputFieldVariants` sizing the input uses, so a column of rows does not shift when one of them opens.
- The action is kept in the DOM at `opacity-0` rather than unmounted, so Tab reaches it. Where there is no hover to reveal it with — a touch screen — it shows unconditionally.

### Validation and messages

`status`, `error` and `hint` render under the value in **both** states, not just while the input is up. A row returns to text as soon as the calendar closes, so a message that only appeared during editing would vanish exactly when the reader needs it.

Precedence matches the default variant: `error` wins over `status`, which wins over `hint`.

<Canvas of={Stories.DetailRowWithHint} />

`required` rejects clearing the date, and `clearable` adds the clear button while the input is up. Both apply to editing only — a row being read has nothing to clear.

Note that `F0InputField` signals an invalid value through the field's border alone: it sets no `aria-invalid`, and a boolean `error` carries no message. Pass `error` as a string, or use `status`, so the reason is announced rather than only coloured.

## Accessibility

### Keyboard interaction

| Key                                 | Result                                                                                                                                                                                  |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| <kbd>Tab</kbd>                      | Moves to the row when the date can be set, or to the request action when it can only be requested. Reaching either reveals it. A read-only row with no request holds nothing focusable. |
| <kbd>Enter</kbd> / <kbd>Space</kbd> | Activates the row: opens the picker on the date already set, with the input focused. On the request action, sends the request.                                                          |
| <kbd>Escape</kbd>                   | Dismisses the calendar and returns the row to text.                                                                                                                                     |

Inside the calendar, keyboard behavior is the default `F0DatePicker`'s.

### Screen reader behavior

- Where the date can be set, the whole row is a single `button` named `Edit {label}`, and the calendar icon is `aria-hidden` — one control with one name, rather than a row wrapping a button.
- Where it can only be requested, the row is not a control; the action is a `button` named `Request a change to {label}`.
- A `readonly` value is a `textbox` with `aria-readonly="true"`, named by `label`, so it is reachable and announced with its value rather than skipped.
- The copy action is named `Copy {label}`, becoming `Copied {label}` with `aria-live="polite"` once the write succeeds.
- Both names are built from `label` through `useI18n()`, so they translate with the rest of the app.
