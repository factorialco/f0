# F0DatePicker

A date field with a calendar. The input reads and accepts a typed date; the calendar opens beside it for picking one. Every value is a range: selecting 30 July 2025 at the `day` granularity selects 30/07/2025 00:00:00 to 30/07/2025 23:59:59, and the same holds for a week, a month, a quarter, a half year or a year. For a duration in hours use [F0DurationInput](?path=/docs/components-inputs-duration-input--documentation); for free-form text use [F0TextInput](?path=/docs/components-inputs-text-input--documentation).

The value is an object, not a `Date`:

```ts
type DatePickerValue = {
  value: { from: Date; to: Date }
  granularity: GranularityDefinitionKey
}
```

`onChange` receives that object and the string the input shows, so a consumer that stores the formatted date does not have to re-format it.

**When not to use**

- **A time of day.** The picker has no clock. Pair it with a time field, or use a component that owns both.
- **A duration.** "Three days off" is a length, not a date; `F0DurationInput` holds lengths.
- **A date the user cannot change.** A read-only date belongs in the detail row's inline presentation, or in plain text, not in a disabled field the user keeps trying to open.
- **A year on its own, far from today.** A birth year or an expiry year is faster to type than to navigate to; a plain number field beats twelve clicks of the year arrow.

### Content best practices

- **Label**: sentence case, no period, naming the date concretely ("Contract end date", not "Date")
- **Placeholder**: leave it out unless the granularity's own placeholder is unclear; the input already shows the expected shape
- **Hint**: one short sentence for a constraint the calendar cannot show, such as why a range is limited

### Granularities

`granularities` lists what the user may pick, and defaults to `["day"]`. Pass more than one and the calendar shows a selector to switch between them; the chosen granularity comes back on the value.

<Canvas of={Stories.WithMultipleGranularities} />

### Presets

`presets` offers named spans beside the calendar. A preset whose granularity is not in `granularities` is dropped, so the two lists stay consistent.

<Canvas of={Stories.WithPresets} />

### Bounds

`minDate` and `maxDate` disable everything outside them and decide the month the calendar opens on.

### Status, hint and clearing

`error`, `status` and `hint` render the same messages as any other field, and `clearable` adds the clear button that empties the value.

<Canvas of={Stories.WithClearable} />

### Controlling the calendar

`open` and `onOpenChange` expose the calendar's state. The picker reports every close through `onOpenChange`, including the one that picking a day causes, so a consumer that drives `open` stays in step.

### Inline variant

`variant="inline"` is the detail-row presentation: a form that reads as rows, where the date prints as text and becomes its own editor when the row activates it. With no `variant`, nothing changes — the field presentation is still the default. The stories live under [DatePicker / Inline](?path=/story/components-datepicker-inline--at-rest).

The variant is presentational only. It holds no mode state: the parent passes `editing`, and the component draws either the date as text or the input with its calendar open. It never closes itself — it reports what the user did through `onDismiss` and keeps the editor on screen until `editing` changes, so the row can keep a field in edit when its value failed to validate.

At rest the date is the exact string the input prints, formatted by `displayFormat` — `"long"` by default (`10 Apr 2026`), `"default"` for `dd/MM/yyyy` — so the text never moves between the two presentations. A coarser granularity prints its own label, such as `April 2026`. An empty value shows the `placeholder` in the secondary foreground colour, and the calendar icon keeps its place, so the date sits at the same x whether it is being read or edited. There is no border, no background and no tab stop at rest: the activator belongs to the row.

`label` stays required. Pass `hideLabel`, as every inline field renderer does, and it becomes the date's accessible name instead of a visible label.

```tsx
const [editing, setEditing] = useState(false)

<F0DatePicker
  variant="inline"
  label="Start date"
  hideLabel
  value={value}
  editing={editing}
  onChange={setValue}
  onDismiss={(reason) => {
    if (reason === "escape") setValue(valueAtActivation)
    setEditing(false)
  }}
/>
```

## Accessibility

- `label` is required. Without `hideLabel` it renders as a visible label; with it, it becomes the input's accessible name, and in the inline variant the name of the date text.
- The calendar opens in a popover that takes focus and returns it to the input, and Escape closes it.
- Days outside `minDate`/`maxDate` are disabled rather than hidden, so their state is announced instead of the date silently disappearing.
- The input stays writable: a date can be typed instead of navigated to, which is the faster path for a keyboard user and the only practical one for a date years away.
