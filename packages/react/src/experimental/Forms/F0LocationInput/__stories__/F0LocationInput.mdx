# F0LocationInput

`F0LocationInput` is the writable address field for forms. The user types an address, picks a suggestion, and the component emits one **structured value** (street, city, state, postal code, ISO-2 country, coordinates) so no product surface has to parse a place result again. It has two modes: a single autocomplete field, or a grouped block with the country on top and the parts below.

The address line is an [F0Select](?path=/docs/components-select--documentation) whose options are the provider's suggestions, so searching, keyboard handling and dialog portalling are the select's. The component makes **no network call and ships no API key**: the consumer injects `searchPlaces` and `resolvePlace`, and without them the address line is a plain text field.

## Guidelines

### Design best practices

#### When to use

- The user enters a postal address that will be stored, shown on a map, or used for geofencing. The structured value keeps every consumer on the same field names.
- International audiences: the same component serves every country, with generic labels the consumer can override through `partLabels`.
- A form already has a country field: pass `fields` without `"country"` and set `defaultCountry` from your own field to scope the search.

#### When NOT to use

- Picking one of the company's existing workplaces or sites. That is a select over records, not an address entry.
- Free-form location notes ("2nd floor, ask for Ana"). Use [F0TextInput](?path=/docs/components-inputs-text-input--documentation).
- Showing a saved address read-only. Render the `formatted` string instead.
- Drawing a geofence radius or dragging a pin. This component stops at the address; put an `F0Map` next to it.

#### Simple vs detailed

Use **simple mode** when a picked suggestion is the whole job: search boxes, filters, quick "where" prompts. Use **detailed mode** whenever the user may need to correct a part, or when the address may not exist in the provider (new buildings, rural addresses, no autocomplete entitlement).

### Content best practices

- Keep the group `label` about the thing, not the action: "Office address", not "Enter address".
- Leave the address `placeholder` unset unless you have a good reason: the default ("Enter an address") is translated and already says what to do.
- Part labels are generic on purpose ("State / region", "Postal code"). Override them through `partLabels` when the product knows the country ("ZIP code", "Province").
- Validation is consumer-side: the component reports `isResolved` but never blocks input.

## Behavior

What `F0LocationInput` guarantees whether it is controlled (`value`) or uncontrolled (`defaultValue`).

### Value model

The value is `F0LocationInputValue | undefined`:

- Text parts: `addressLine1`, `addressLine2`, `city`, `state`, `postalCode`.
- `country`: lowercase ISO-2 code (`"es"`), typed as `CountryCode`.
- `formatted`: a display string. It comes from `resolvePlace` after a pick and is reassembled locally once the user edits any part.
- Resolution data: `placeId`, `latitude`, `longitude`, `timezone`. Present only while the value is exactly what the provider returned.
- `undefined` when every part is empty and no country is selected.

Every `onChange` carries `meta`:

- `source`: `"picked"` right after a suggestion resolves, `"typed"` for any manual edit.
- `isResolved`: whether `placeId` and both coordinates are still present.

### Editing invalidates the pick

Editing a part that moves the pin - the address line, city, state, postal code or country - drops `placeId`, `latitude`, `longitude` and `timezone` and emits `{ source: "typed", isResolved: false }`. The typed text is kept. Consumers that need coordinates for a typed address geocode it themselves.

`addressLine2` is the exception: a floor or apartment number refines the address inside the same building, so it keeps the picked place and still reports `isResolved: true`. Any part added to the component later invalidates by default.

<Canvas of={Stories.Controlled} />

### Picking a suggestion

Typing happens in the select's search box: two or more characters search after a 250 ms debounce, out-of-order responses are discarded, and results are listed exactly as the provider returned them (no local filtering, which would drop accent variants). Each suggestion is one line: a `description` is appended to the `label` rather than shown under it, so a list of addresses stays scannable.

A pick shows the suggestion on the trigger right away but emits nothing until `resolvePlace` returns; the resolved value replaces the whole value, country included, with `{ source: "picked", isResolved: true }`. If `resolvePlace` is missing, rejects or returns nothing, the suggestion label is kept as the address line and the change is reported as typed.

### Only a suggestion can be chosen

The list offers exactly what the provider returned: there is no create action, so the field cannot invent an address. When the search comes back empty it says so and nothing changes.

A stored value that no suggestion covers is still displayed (the trigger reads the value, not a matching option) and stays editable through the parts in detailed mode. A surface that must accept addresses the provider does not know should omit `searchPlaces`, which turns the address line into a plain text field.

### Country and search scope

`searchPlaces(query, { country })` receives the value's country, else `defaultCountry`, else the single entry of `countries`. Changing the country clears the cached suggestions.

<Canvas of={Stories.RestrictedCountries} />

### Without a provider

Omit `searchPlaces` and the address line is a plain [F0TextInput](?path=/docs/components-inputs-text-input--documentation): nothing to open, no network. This is how a surface without the autocomplete entitlement renders the same form.

<Canvas of={Stories.WithoutAutocomplete} />

### Inside a dialog

`F0Select` portals its own dropdown into the surrounding centered or fullscreen `F0Dialog`, so a click on a suggestion is never read as a click outside.

## Accessibility

The address line inherits `F0Select`'s contract: the trigger is a `combobox`, the dropdown is a `listbox` of `option` rows, and the search box inside it is focused on open.

### Keyboard interaction

| Key                               | Result                                                  |
| --------------------------------- | ------------------------------------------------------- |
| `Enter` or `Space` on the trigger | Opens the dropdown with the search box focused          |
| Typing                            | Searches after two characters; results replace the list |
| `ArrowDown` / `ArrowUp`           | Moves through the options                               |
| `Enter`                           | Picks the highlighted option                            |
| `Escape`                          | Closes the dropdown and keeps the current value         |

### Screen reader behavior

- Each part carries its own label. In detailed mode they are grouped in a `fieldset` named by `label` through `aria-label`, so a part is announced within its group without a visible title.
- The empty state says which state the list is in: waiting for input, searching, or no results.
- Without `searchPlaces` the address line is announced as a plain text field.
