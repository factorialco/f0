# Resource page

Composes the body of a page about one resource (a person, a team, a workplace, a role, a legal entity) in a fixed order, so every resource page reads the same way: notice, header, tabs, then the content beside its right-hand rail. Mount it in the `children` of `Navigation/Page`, whose `header` slot keeps the `PageHeader` and its breadcrumbs. For a list, a dashboard or a settings area, compose `Layout.Page` directly instead, without a resource header.

## Anatomy

Top to bottom: `alert` sits above everything because it must be read first; the resource header carries the avatar, name, status, description and the action row; `tabs` appear only when the page is split into parts, like Overview and People on a team; `children` renders beside `aside`. There is deliberately no type label in the header, because the breadcrumb, the avatar and the page's own shape already say what this is.

### Content best practices

- **Description** is the resource's own description when one exists; otherwise its single most identifying fact, like a member count. Never generated filler.
- **Status** belongs only to resources that genuinely have a lifecycle. Do not invent states for things that cannot change state.
- **Leave a slot out** when it has no honest content. An absent owner is better than a guessed one.

### Behavior

- **The order is fixed** and owned by the component, so it cannot drift page by page.
- **The header stays at the top** while the content scrolls under it, so the resource you are working on is always named. The tab strip is deliberately not sticky: inside the sticky box it would inherit the header's height tween, lagging behind the scroll and sitting over the content for as long as the tween ran.
- **The header condenses as the content scrolls.** Over the first 96px the metadata fades and collapses away, the avatar drops two sizes, the name and the role each step down a size, the gap between them closes and the space down to whatever follows tightens from 20px to 12px; scrolling back up walks all of it in reverse. It is tied to the scroll position rather than tweened over time, so nothing under the header lags behind it, and every size is a function of that one number, so they all land together on the same frame. It is scroll _position_, not direction: the header is as condensed as the page is scrolled.
- **The header's bottom border follows the tabs.** With a tab strip present the header drops its border, because the strip already separates the header from the content. Set `showBottomBorder` yourself to override.
- **The action row reads history, overflow, secondary, primary on desktop**, with the primary action rightmost. On mobile the actions stack by priority instead, primary first, and the history button sits above close.
- **`aside` decides the column count.** With a rail the body is two columns and the rail collapses above the content on narrow viewports; without one the content takes the full width rather than leaving an empty column. There is no rule drawn between the columns: the rail is navigation, not a panel bolted to the page.
- **The page owns the rail, not the caller.** `aside` takes the sections, and the page renders the table of contents over them. Marking the section being read and scrolling to a picked one both need the scrollport and the live height of the chrome, and only the page has those, so a caller passing its own rendered list could never do either.
- **The rail follows the scroll.** The active entry is the last section whose top has passed under the chrome, which is the heading you would look up to from wherever you are. Each entry's id is the `id` of a section in `children`, and picking one scrolls that section to just under the chrome rather than under it.
- **The rail pins itself under the chrome** and scrolls inside the height that is left, so a long table of contents never makes the page taller. Its offset is measured, since the chrome shrinks as the header condenses.
- **The columns are composed by this component**, not by `TwoColumnLayout`: that layout wraps the pair in its own scrollport, which a sticky rail has nothing to stick to.

## Accessibility

- **The rail is announced as a complementary region**, so screen reader users can jump to it or skip past it. On desktop it comes after the main column in the reading order.
- **The resource name is not a heading.** `ResourceHeader` renders the title as a styled `span`, so a resource page currently has no `h1` and its heading outline starts at the `h2` of the first section. Raised with Foundations; it needs a change in `BaseHeader` because it affects every header in the product.
- **The history button is icon-only on desktop.** It keeps its accessible name through `F0Button`'s `hideLabel` handling (an `aria-label`, a visually hidden label and a tooltip), and it is labelled outright in the mobile stack.
- **The tab strip is announced as a navigation region**, so screen reader users can reach the page's parts directly.
- **The condensed metadata is hidden from assistive tech**, not merely made 0px tall: while closed the rows carry `aria-hidden`, so they are skipped rather than read out as invisible text.
- **The condensing respects reduced motion.** With `prefers-reduced-motion` the header still condenses, it just changes without the tween.
