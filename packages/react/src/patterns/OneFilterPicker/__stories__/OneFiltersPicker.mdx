# FilterPicker

Narrows a collection by several independent criteria and exposes saved filter
combinations as presets. Edits are staged in a popover and only reach the host on
"Apply filters", so a server-backed collection refetches once per commit instead
of on every keystroke. `OneDataCollection` already composes this pattern through
its `filters` and `presets` props; for a single free-text lookup use a search
input, and for one-of-N navigation between views use tabs.

## Anatomy

The picker renders three parts in one row: the **Filters** trigger (opens the
popover with the filter list and the form of the selected filter), the **presets
row** (one pill per saved view, collapsing into an overflow dropdown when the row
runs out of space), and the **chips row** below (one chip per applied filter plus
a Clear action).

### Filter definition API

`FiltersDefinition` is a record of filter key to filter definition. Every
definition carries a `label` (read in the filter list, in the chip, and in the
accessible summary of applied filters), a `type`, the options of that type, and
optionally `hideSelector`.

`hideSelector: true` keeps a filter out of the popover list while its value still
applies and is still emitted. It exists for keys that are written by something
else: nested child selections of an `in` filter, or a value driven entirely from
the URL or from the page context.

A realistic definition for an employee directory:

```tsx
const filters = {
  name: { type: "search", label: "Employee name" },
  department: {
    type: "in",
    label: "Department",
    options: {
      // Departments change rarely, so resolve them once per session
      cache: true,
      options: async () => fetchDepartments(),
    },
  },
  location: {
    type: "in",
    label: "Office location",
    options: {
      options: [
        { value: "barcelona", label: "Barcelona" },
        { value: "london", label: "London" },
        { value: "remote", label: "Remote" },
      ],
    },
  },
  startDate: {
    type: "date",
    label: "Start date",
    options: { mode: "range" },
  },
} as const satisfies FiltersDefinition
```

**Options loading.** Options of an `in` filter are not cached by default: they are
resolved every time the filter is opened, and again to build the label of each
chip. For anything larger than a hardcoded list, either set `cache: true` or
cache in the loader.

**The number value shape** is the least obvious part of the API. A number filter
emits either a single value or an interval where each bound records whether it is
`closed` (inclusive) or open (exclusive), following the
[mathematical definition of open and closed intervals](<https://en.wikipedia.org/wiki/Interval_(mathematics)#Definitions_and_terminology>).
Both bounds are independent and either can be `undefined`, which makes the
interval unbounded on that side.

```tsx
// Salary equal to 45000
{ mode: "single", value: 45000 }

// 30000 <= salary < 45000
{
  mode: "range",
  from: { value: 30000, closed: true },
  to: { value: 45000, closed: false },
}

// salary > 30000, no upper bound
{
  mode: "range",
  from: { value: 30000, closed: false },
  to: { value: undefined, closed: true },
}
```

### Presets API

A preset is a saved snapshot of the collection view. Clicking one **replaces**
the whole filter state, so a preset must only reference keys that exist in the
filter definition.

**Two selection models.** Without `selectedPresetId`, a preset shows as selected
only while the applied filters match its `filter` exactly, and the chips row is
hidden because the pill already represents those filters. Changing anything on
top of it deselects every preset. With `selectedPresetId` and `onSelectPreset`,
selection is identity-based: the preset stays selected while state changes on top
of it and the chips stay visible, so the difference from the saved view is
readable. Use identity-based selection whenever a preset captures more than
filters, since only the owner can apply sorting, grouping and visualization.

Pass `itemsCount` when the size of each saved view is decision-relevant, for
example a pending-approvals row where an empty view means there is nothing to do.

### Content best practices

- **Filter label**: sentence case, no colon, a noun phrase naming the attribute.
  The label is reused verbatim in the chip and in the accessible summary of
  applied filters, so it has to read correctly in both.
  - **Correct:** "Office location", "Employee name", "Start date"
  - **Incorrect:** "Filter by location", "loc", "emp_name"
- **Option label**: the name people recognise, not the stored value. The `value`
  is what the backend receives, the `label` is what is read on screen.
  - **Correct:** "Human Resources", "Barcelona"
  - **Incorrect:** "hr", "office_bcn"
- **Preset label**: name the question the view answers in two to four words.
  Never number presets, and never repeat the filter name in every pill.
  - **Correct:** "On probation", "Contract ending in 30 days"
  - **Incorrect:** "Preset 1", "Filter: probation"
- **Preset description**: one sentence stating what the view contains, used in
  the preset form when the label alone is ambiguous.

### Behavior

- Edits inside the popover are staged in a local draft. Nothing reaches
  `onChange` until "Apply filters" is pressed; closing the popover discards the
  draft. The Clear inside the popover only empties the draft, so it still needs
  "Apply filters" to take effect. Removing a chip, the Clear in the chips row and
  clicking a preset commit immediately.
- Only active filters are committed. A cleared picker emits `{}` rather than a
  state full of empty values, so a data source does not receive a filter that
  matches nothing.
- Commits are optimistic by default: the chips and the presets row update even
  when the host only observes `onChange` and never echoes the next `value`. A
  later change of the `value` prop re-seeds the applied state, which stays the
  source of truth.
- The draft is re-seeded only when the content of `value` changes, not when its
  identity changes, so a host that rebuilds the object on every render does not
  wipe an in-progress edit.
- Removing the chip of an `in` filter also clears the nested child keys of its
  selected options, so no orphaned values reach the backend.
- The presets row is wrapped in an error boundary. If it throws while rendering
  it is hidden and logged instead of unmounting the collection and its fetching.
- `OneFilterPicker<Definition extends FiltersDefinition>` is generic over the
  filter definition. `value` and the argument of `onChange` are
  `FiltersState<Definition>`, which is every key of the definition made optional.
  Read the value type of a single filter with
  `FilterValueByKey<Definition, "department">`. Declare the definition with
  `as const satisfies FiltersDefinition` to keep the keys literal, otherwise
  `Definition` widens to `Record<string, FilterDefinition>` and typos in preset
  filters stop being caught.

### Extending the pattern

Filter types are pluggable. To add one:

1. Create a folder under `OneFilterPicker/filterTypes` and export a
   `FilterTypeDefinition` from its `index.tsx`.

```tsx
export const myFilter: FilterTypeDefinition<number> = {
  // Value returned when the filter is not set
  emptyValue: 0,
  // Form rendered inside the popover for this filter
  render: (props) => <MyFilterForm {...props} />,
  // Decides whether the filter is committed and whether a chip is rendered
  isEmpty: (value) => value === undefined || value === 0,
  // Value part of the chip label; may return a promise
  chipLabel: (value) => value.toString() ?? "-",
}

export type MyFilterDefinition = BaseFilterDefinition<"myFilter">
```

2. Register it in `filterTypes/filters.tsx`.

```tsx
import { myFilter, MyFilterDefinition } from "./MyFilter"

export const filterTypes = {
  in: inFilter,
  search: searchFilter,
  date: dateFilter,
  number: numberFilter,
  myFilter,
} as const
```

3. Add it to `FilterDefinitionsByType` so definitions of that type typecheck.

```tsx
export type FilterDefinitionsByType = {
  // ...
  myFilter: MyFilterDefinition
}
```

4. Add its value type to `FilterValue`, which is what `FiltersState` resolves per
   key.

```tsx
export type FilterValue<T extends FilterDefinition> =
  T extends InFilterDefinition<infer U>
    ? U[]
    : T extends SearchFilterDefinition
      ? string
      : T extends DateFilterDefinition
        ? Date
        : T extends MyFilterDefinition
          ? number
          : never
```

Set `formHeight` on the definition when the form needs more room than the
default: the popover sizes itself to the tallest form in the definition.

### Screen reader behavior

- The trigger is a toggle button. It carries its pressed state while the popover
  is open and `aria-controls` pointing at the popover id, which is only set while
  open so the reference never dangles.
- When filters are applied the trigger also gets `aria-describedby` pointing at a
  visually hidden description that lists the labels of the active filters. That
  description is built from the filter labels, so a vague label degrades the
  announcement.
- The popover content is labelled with the localized "Filters" label, so it is
  announced as a named group rather than an anonymous dialog.
- Each applied filter is a chip button whose accessible name is
  `"Label: value"`, for example "Department: Engineering". The close affordance
  inside the chip removes that filter.
- In `compact` and `inline` modes the trigger label is visually hidden and the
  applied-filters indicator is a decorative dot with no text equivalent. The
  accessible name comes from the localized label plus the applied-filters
  description, so do not rely on the dot alone: set `displayCounter` when the
  number of applied filters matters.
- Presets that overflow move into a dropdown button, so a collapsed preset is
  still reachable by keyboard. The count in a pill is rendered as text and read
  after the preset label.
- The pattern localizes only its own chrome (Filters, Apply filters, Clear, the
  results prefix). Filter labels, option labels and preset labels come from the
  consumer and must already be translated.
