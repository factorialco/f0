# F0CarouselDialog

One dialog you **walk through**: an arrow on each side of the panel, the position
in the header, and the content swapped underneath without the dialog ever closing.

---

## Anatomy

An `F0Dialog` with two additions — a reading beside the close button, and a
control outside each edge of the panel.

<Canvas of={Stories.Default} />

| Element     | Description                                                           | Required |
| ----------- | --------------------------------------------------------------------- | -------- |
| Title       | The current page's title, in the header and as the accessible name    | Yes      |
| Position    | "3 of 11" beside the close button; hidden when there is only one page | Auto     |
| Side arrows | Previous / Next, outside the panel, disabled at the ends              | Auto     |
| Content     | The current page only — one item is mounted at a time                 | Yes      |

## Guidelines

**It is for a set, not for a sequence.** Use it where a reader moves _between_
things: a post opened from a feed, one photo of many, a record and the next
record. A wizard's steps are one task with a beginning and an end — that is
`F0Wizard`, which knows about progress and about not letting you skip.

**The arrows are outside the panel,** which is the whole reason this is a
component rather than two buttons in someone's `children`. Inside, they compete
with the content for attention and for width; beside it, they are unmistakably
chrome. They are still rendered _within_ the dialog's own element, so the focus
trap holds and the keyboard reaches them.

**The index is controlled.** The thing you opened the dialog on is already state
the app holds — the post that was clicked — and a dialog keeping its own copy of
it is two answers to one question. An id that names nothing falls back to the
first item, so a page deleted underneath you leaves the dialog on something
rather than empty.

**Let the content name itself, or let the header do it — not both.** Components
that render their own title (`CommunityPost`) take a `hideTitle` prop for exactly
this. Always pass the item a `title` regardless: it is the dialog's accessible
name.

### When not to use

Not for steps of one task, and not where the reader needs to compare pages side by
side, since only one is ever visible.

A set that happens to hold **one** item is fine, though — it quietly becomes an
ordinary dialog rather than growing two dead controls, so you don't have to branch
on the length of your own data.

## Accessibility

The arrows are children of the dialog panel, positioned outside its box rather
than portalled beside it: anything outside a modal's content is `aria-hidden` and
inert, so arrows rendered "next to" the dialog would be unreachable by keyboard
and invisible to a screen reader.

**The arrow keys work**, bound while the dialog is open, because that is what
anyone who has used a photo viewer tries first — and they stand down while focus
is in a text field, whose own caret movement is the more specific claim on those
keys.

Both arrows keep their places at the ends and go `disabled` rather than
disappearing. The current page's `title` is the dialog's accessible name even when
`hideTitle` on the content keeps it out of view.

On a phone the dialog is a bottom sheet with no room beside it, so the arrows move
onto the panel's own edges — where a gallery has always put them.
