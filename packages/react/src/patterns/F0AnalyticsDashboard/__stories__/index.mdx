### Widget information hints

Use `info` for the definition of the figure itself. A string reveals a short
tooltip; structured content reveals a titled card with an optional link to the
definition's source. Keep this separate from `description`, which states what
the widget shows, and `explanation`, which documents how the result was
calculated.

In the story below, hover or focus the information icons beside **Headcount by
Department** and **Avg. Salary**. The other widgets intentionally omit `info`,
so the new affordance can be compared with the unchanged header.

<Canvas of={Stories.MixedDashboard} />

- WHEN an item provides `info` → THEN an information trigger appears beside its title on chart, metric, and collection widgets.
- WHEN `info` is omitted → THEN the header layout and interaction remain unchanged.
- WHEN the widget is in an error state → THEN the information trigger remains available to explain what the failed widget was meant to measure.
- WHEN the title is long → THEN it truncates around the fixed-size trigger instead of pushing the trigger out of the header.

### Ask One from a widget

When an enabled AI chat is mounted, each titled widget adds **Ask One** to its
actions menu. Choosing it opens the chat and places the widget title in the
composer's quote chip, ready for a question.

**Menu action**

The story leaves the widget menu open so the action, icon, and placement can be
reviewed directly.

<Canvas of={AskOneStories.WidgetMenuAction} />

**Quoted in the chat**

This story completes the action and leaves the resulting quote visible in the
real chat composer.

<Canvas of={AskOneStories.WidgetQuotedInChat} />

**Drag shortcut in edit mode**

On a multi-item editable dashboard, dragging a titled widget into the visible
chat is a pointer shortcut for the same action. The automated story finishes
with the quote visible and the dashboard order unchanged.

<Canvas of={WidgetDropStories.DragWidgetToQuote} />

Pass `onAskAi` when the host needs to own the action instead of sending it to
the mounted chat:

```tsx
<F0AnalyticsDashboard
  items={items}
  onAskAi={({ id, title }) => {
    openProductChat({ widgetId: id, quote: title })
  }}
/>
```

Pass `onAskAiTarget` when the mounted chat should keep the built-in quote,
open, and focus behavior while the host attaches structured analytical
context. The observer receives the widget identity plus the exact `quote`
object staged in the composer. Point asks also include the raw `point`.

```tsx
<F0AnalyticsDashboard
  items={items}
  onAskAiTarget={({ id, point, quote }) => {
    attachAnalyticalContext({ widgetId: id, point, quote })
  }}
/>
```

<Canvas of={AskOneStories.TargetObserver} />

If both callbacks are supplied, `onAskAi` owns the interaction:
`onAskAiTarget` is not invoked and F0 does not stage a built-in quote.

- WHEN an enabled AI chat is mounted and a widget has a title → THEN its actions menu includes **Ask One**.
- WHEN a widget is in an error state but still has a title → THEN **Ask One** remains available from its error header.
- WHEN no chat is available and `onAskAi` is omitted → THEN the action is hidden instead of offering a dead command.
- WHEN **Ask One** uses the built-in behavior → THEN the dashboard exits widget fullscreen, quotes the title, and opens the chat.
- WHEN `onAskAi` is provided → THEN the action calls the host with the widget `id` and `title` without changing chat or fullscreen state.
- WHEN `onAskAiTarget` observes the built-in behavior → THEN it receives the widget `id`, `title`, and exact pending `quote` before F0 stages that quote, without replacing any chat behavior.
- WHEN a directly rendered widget has `onAskAi` but no `itemId` → THEN the action is hidden rather than sending an empty ID.
- WHEN a widget is dropped on chat → THEN it follows the same built-in,
  observed, or host-owned behavior as the menu action.
- WHEN the reorder grip is only clicked → THEN no drag invitation appears and
  no widget action runs.
- WHEN the pointer drag is cancelled or ends outside chat → THEN no quote or
  host action is created.
- WHEN a widget has no title → THEN the action is hidden because there is nothing to quote.

### Ask One from a chart point

Charts with an available chat or `onAskAi` handler let the reader click a mark
before choosing **Ask One**. The intermediate action is intentional: ordinary
chart exploration must not open the chat on every click.

**Interactive point flow**

In this story, click the Engineering bar to reveal the anchored action. Choose
**Ask One** to review the category, series, and formatted value in the focused
chat composer.

<Canvas of={AskOneStories.ChartPointFlow} />

The host-owned callback receives the raw point as `point`, in addition to the
widget `id` and `title`. `point.values` preserves every measure carried by one
mark, while `point.series` preserves every visible series resolved by a line
chart click. `point.source` is always `"pointer"`.

```tsx
<F0AnalyticsDashboard
  items={items}
  onAskAi={({ id, title, point }) => {
    openProductChat({ widgetId: id, quote: title, point })
  }}
/>
```

- WHEN a pointer user clicks a chart mark → THEN **Ask One** appears beside that mark without opening the chat yet.
- WHEN no mark has been clicked → THEN no Ask One trigger stands over the chart waiting to be revealed.
- WHEN the built-in action is chosen → THEN the quote keeps the chart title, visible point context, and tooltip-formatted values, opens the chat, and focuses its composer.
- WHEN a scatter point is quoted → THEN both the X and Y measures are included with their axis names and formatters.
- WHEN a line category is quoted → THEN every visible series at that category is included, matching the axis tooltip.
- WHEN `onAskAi` owns the action → THEN it receives the raw point and the built-in chat state remains unchanged.
- WHEN `onAskAiTarget` observes the built-in action → THEN it receives that exact pending quote together with the raw point.
- WHEN the chart has no title → THEN the anchored action is not offered because there is no widget context to quote.
- WHEN the chart moves because of scrolling or resizing, or the reader presses <kbd>Escape</kbd> or clicks elsewhere → THEN the anchored action closes.

### Report filters

Report filters are one applied state shared by every participating item. Pass `filtersValue` with `onFiltersChange` to own that state — for example to hydrate a saved report and persist each committed change — or pass only `defaultFilters` to let the dashboard own it.

```tsx
const [filtersValue, setFiltersValue] = useState<FiltersState<typeof filters>>(
  savedReport.filters
)

<F0AnalyticsDashboard
  filters={filters}
  filtersValue={filtersValue}
  onFiltersChange={setFiltersValue}
  items={items}
/>
```

- WHEN `filtersValue` is provided → THEN the dashboard is controlled and waits for the parent to pass each committed value back.
- WHEN only `defaultFilters` is provided → THEN the dashboard owns subsequent committed filter state.
- WHEN Apply, Clear, chip removal, or a preset commits a change → THEN `onFiltersChange` receives the next applied state and participating items refetch with it.
- WHEN the picker closes without applying → THEN temporary selections are discarded.
- WHEN an item sets `useDashboardFilters=false` → THEN that item fetches with an empty filter object.
- WHEN `items` is empty → THEN the filter bar remains usable without a grid item fetch.

### Widget filters

Use `itemFilters` when a filter is scoped to exactly one widget. The prop is a
resolver, so the host can enable it only for supported items and return
`undefined` everywhere else. F0 owns the picker draft and the hover/focus
header action; the host owns the applied state, data refetch, and persistence.

```tsx
<F0AnalyticsDashboard
  items={items}
  itemFilters={(item) => {
    if (!canFilterWidget(item)) return undefined

    return {
      filters: definitionsFor(item),
      value: savedFiltersByItem[item.id] ?? {},
      onChange: (value) => updateWidgetFilters(item.id, value),
    }
  }}
/>
```

- WHEN the resolver returns `undefined` → THEN the widget is unchanged and has no filter control.
- WHEN it returns a configuration → THEN metric, chart, collection, and error-state headers expose the same anchored filter picker.
- WHEN the host supplies catalog-backed `in` or `date` definitions → THEN widget filters use the same selectable values and date controls as report filters.
- WHEN a draft is dismissed → THEN the applied widget query remains unchanged.
- WHEN Apply commits a draft → THEN only that widget's callback runs; F0 does not merge it into report filters.
- WHEN report and widget filters both exist → THEN the host composes them in the data-source query according to its own semantics.
- WHEN filters are applied → THEN the trigger counter reports how many filter fields are active without rendering their selected values in the widget header.
- WHEN a hover-capable widget is hovered or the trigger receives keyboard focus → THEN the filter icon appears with the other widget actions and remains visible while its popover is open; touch-only devices keep it visible.

### Screen reader behavior

- The filter trigger keeps the stable name "Filters"; applied filter labels are exposed as its accessible description, while a visible counter shows how many report filters are active.
- The filter popover has a dialog name, and filter options expose native checkbox semantics.
- Applied filter removal buttons keep the stable name "Close"; the filter label and selected value are exposed as their accessible descriptions.
- Widget filter rows announce whether their draft is active, the compact list moves focus to its first control when opened, and returning from an editor restores focus to its row (or the next available row if the definition disappeared).
